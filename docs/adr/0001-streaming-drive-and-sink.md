# 0001 网盘读取和存放写入改为顺序流

状态：已接受（2026-10-12）

## 背景

安装一款游戏，是从网盘把分卷压缩包读出来、解压、写到存放目录。现在两头都按"一小块一次往返"实现：

- 读取：`DrivePlugin::read_at(file_id, offset, length)` 是唯一的读取方式。百度插件每次调用都先请求 `filemetas` 取下载地址，再新建 HTTPS 连接发一次 `Range` 请求。解压器每次只要 8–32 KB，于是 30 GB 的包要发约 200 万次 HTTPS 请求，还会触发百度限频。
- 写入：`write_continuing` 每写一块都先 `SIZE` 查远端大小，再新开一条 FTP 数据连接 `APPE`。
- ZIP 目录：`scan_zip` 从头逐个读本地文件头，几千个文件就是上万次请求。
- 容量：ZIP64 和超过 4 GB 的单个文件直接拒绝安装，而 PS5 游戏两者都很常见。

这些问题的根源是接口形状，不是某个函数的实现，所以要先改接口。

## 决定

### 1. 读取：网盘插件提供顺序读取流

`DrivePlugin` 增加：

```cpp
class ByteStream {
 public:
  virtual ~ByteStream() = default;
  // 读到 n 字节或文件结束才返回。返回实际读到的字节数，出错时设置 error。
  virtual std::size_t read(std::uint8_t* dst, std::size_t n, std::string* error) = 0;
  virtual std::int64_t position() const = 0;
};

virtual std::unique_ptr<ByteStream> open_stream(const std::string& file_id, std::int64_t offset,
                                                const CancelToken& cancel, std::string* error) = 0;
```

`read_at` 保留，只用于读 ZIP 末尾目录、文件开头签名这类少量随机读。

百度插件的实现：

- 下载地址按 `fs_id` 缓存，记下取得时间。6 小时内复用；遇到 403、410 或百度表示地址失效的错误码时重新获取。整个安装过程里，`filemetas` 只在每个分卷第一次打开和地址过期时调用。
- 一个流对应一次 `Range: bytes=<offset>-` 请求，按需从同一个响应体里 `WinHttpReadData`，一个分卷从头读到尾只用一条连接。
- 读取出错时，从当前位置重新获取地址、重新建连，最多重试 5 次，间隔 1、2、4、8、16 秒。重试对上层透明。
- WinHTTP 会话在插件实例里长期持有，复用 TCP 和 TLS。

`http.hpp` 增加一个持有会话的 `HttpClient`，提供一次性请求和流式响应两种用法；原来的 `http_send` 改成调用它。

### 2. 预读：下载和解压、写入并行

在网盘流和解压器之间加一层 `PrefetchReader`：

- 后台线程从 `ByteStream` 读，每块 4 MB，最多攒 8 块（PC 默认 32 MB）。PS5 版可以把块数调小。
- 解压器从内存块里取数据，任意小的读取都不碰网络。
- 下载和"解压加写入"同时进行。否则总耗时是两者相加，并行后接近两者中较慢的那个。

跳转的处理：

- 向前跳不到 1 MB 时，读出来丢掉。
- 其余情况关闭当前流，在新位置重新打开。用于 RAR 跳过已完成的文件、ZIP 定位到某个条目。

### 3. ZIP：读中央目录

- 用 `read_at` 读最后一个分卷末尾最多 64 KB，找到目录结束记录；有 ZIP64 定位记录时，再读 ZIP64 目录结束记录。
- 一次读出整个中央目录，拿到每个条目的大小、CRC、所在分卷号和本地文件头偏移。大小和 CRC 以中央目录为准，因此"文件头里没写大小"（标志位 8）的条目也能处理。
- 解压时按（分卷号，偏移）排序，顺序流过压缩包；每个条目的本地文件头在流里顺手读掉，用来算数据起点。
- 分卷 ZIP 的偏移按分卷号分别计算，不再把所有分卷当成一段连续数据。
- 所有大小和偏移改成 64 位，去掉 4 GB 限制。RAR 一侧同样去掉"单个文件超过 4 GB 不能安装"的判断。

### 4. 写入：一个文件一个写入流

`InstallSink` 增加：

```cpp
class FileWriter {
 public:
  virtual ~FileWriter() = default;
  virtual std::string write(const std::uint8_t* data, std::size_t size) = 0;
  // 正常结束时调用。FTP 在这里关闭数据连接并确认 226。
  virtual std::string finish() = 0;
};

virtual std::unique_ptr<FileWriter> open_writer(const std::string& path, std::string* error) = 0;
```

- 本机目录：打开一次文件，连续写，`finish` 时关闭。
- FTP：`open_writer` 时发一次 `STOR` 并打开数据连接，之后的 `write` 只往数据连接里发数据，`finish` 时关闭并读 226。每个文件固定 3 次命令往返，和文件大小无关。
- 删除 `write_continuing` 和每块一次的 `SIZE` 检查。

续传仍按文件为单位：中断时没写完的文件从头再写，已经校验通过的文件跳过。这和现在实际的行为一致，只是不再假装能从文件中间接着写。

### 5. 进度日志：只追加

- 日志改为 `.panplay-journal.jsonl`，每完成一个文件追加一行。FTP 用 `APPE`，每个文件一次往返。
- 读取时忽略无法解析的最后一行，这是中断造成的半行。其余行损坏时把整份日志当作空的，已完成的文件会重新解压校验，结果仍然正确。
- 去掉 1 MB 的读取上限。

### 6. 取消

`CancelToken` 从安装任务一路传到网盘流、预读线程和写入流。取消时关闭网络句柄，让阻塞中的读写立刻返回。暂停就是"取消 + 保留暂存区"，界面和队列放在下一步，但 P0 先把取消路径打通。

### 7. 百度会话

预读线程会在长时间安装中刷新令牌，所以百度插件改为进程内单例：刷新令牌时加锁，刷新前先重读会话文件；会话文件先写临时文件再改名。

## 测试

假网盘改造：

- 内容由生成函数按偏移现算，不放进内存，因此可以模拟超过 4 GB 的文件和 ZIP64 包。
- 可以配置每次请求的延迟，并统计 `filemetas` 次数、流的打开次数和 `read_at` 次数。
- 可以在指定位置注入断线和地址失效。

自测里加以下断言：

- 读 1 GB 时，流的打开次数不超过分卷数加重试次数，`read_at` 次数是个位数。
- 有几千个小文件的 ZIP，扫描目录只需要个位数的读取。
- 用 ZIP64 包和含超过 4 GB 单个文件的 RAR 能安装成功，CRC 正确。
- 中途断线后自动重连，最终结果正确；取消后能在 1 秒内停下。
- FTP 写入：每个文件的命令往返次数是固定值，不随文件大小增长。

## 验收

- 用一款含超过 4 GB 单个文件的真实游戏，从百度装到 dummy FTP，一次成功。
- 安装期间 `filemetas` 的调用次数约等于分卷数。
- 本机测速时，下载速度接近同一网络下浏览器直接下载这个分卷的速度。

## 影响

- `zip_install.cpp`、`rar_install.cpp`、`install_sink.cpp`、`baidu_drive.cpp`、`http_winhttp.cpp` 都要改，RAR 读取回调改为经过预读层。
- 进度日志的文件名和格式变了。旧格式的日志读不出来时按空日志处理，已完成的文件会被重新解压一遍。
- 内存占用增加约 32 MB 的预读缓冲。

## 实测后补充（PPSA05106，1.5 GB RAR，解压后 3 GB）

- UnRAR 默认的“快速打开”会在读每个文件头前跳到包尾读索引，再跳回来，一个包重连 50 多次。打开压缩包时关掉（`dll.cpp` 里 `QOpenMode=QOPEN_NONE`）。
- UnRAR 读完文件头会往回退几十字节重读。预读层保留刚读完的一块，往回跳不出这块就不重连；往前跳 8 MB 以内也不重连，直接丢弃中间数据。
- dlink 每次都会重定向到下载节点。记下节点地址，后续请求直接发过去，单次小范围读从约 0.55 秒降到约 0.14 秒。
- 列 RAR 目录改为按需小范围读（每次 64 KB），不开长连接。
- 结果：安装从 104 秒降到 35～45 秒。解压期间写出约 2 秒、解压加校验约 7 秒，其余时间都在等下载；单连接下载在 33～53 MB/s 之间波动。

设置环境变量 `PANPLAY_TRACE` 后，安装会在标准错误里打印重连、跳转和各阶段耗时。

## 已定

1. 续传粒度保持按文件，不做"大文件从中间续"。
2. 单连接时预读缓冲 4 MB × 8 块（32 MB）就够了（多连接的默认值见第 3 条）。`panplay bench-prefetch` 模拟下载每 48 MB 卡 0.4 秒、写入每 32 MB 换文件卡 0.3 秒，256 MB 数据：

   | 缓冲 | 下载 40 / 写 60 MB/s | 下载 60 / 写 60 MB/s |
   |---|---|---|
   | 256 KB | 36.7 秒 | 36.5 秒 |
   | 4 MB × 1 | 15.6 秒 | 13.8 秒 |
   | 4 MB × 2 | 10.6 秒 | 9.3 秒 |
   | 4 MB × 4 | 9.1 秒 | 7.5 秒 |
   | 4 MB × 8 | 8.9 秒 | 7.0 秒 |
   | 4 MB × 16 | 8.9 秒 | 7.0 秒 |

   32 MB 已经能盖住两边的卡顿，再大没有收益。PS5 版内存紧时可以降到 4 MB × 4。
3. ~~一个分卷只用一条连接~~ → 改为多连接，默认 8 条，每块 8 MB，最多 16 块（约 128 MB）。单连接实测只有 30～39 MB/s，补上上面几项修复后，下载成了唯一瓶颈。多连接时每条连接领一块，用有界 Range 请求下完；下完的块按偏移顺序交给读取方，解压看到的仍是顺序流，续传仍按文件。

   纯下载 20 秒（`panplay bench-download`）：1 条 30～39 MB/s，4 条 36～53，8 条 52～58，16 条 46。
   真实安装 PPSA05106 到本机目录：1 条 55 秒，4 条 32 秒，8 条 26 秒；经 FTP 走服务端 36 秒（改造前 163 秒）。
   多开没有收益，还容易被百度限速，所以不超过 8 条。命令行可用 `--connections`、`--block-mb`、`--blocks` 调整。
