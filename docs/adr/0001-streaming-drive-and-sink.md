# 0001 网盘读取和存放写入改为顺序流

状态：已接受（2026-10-12）

## 背景

安装一款游戏，是从网盘把分卷压缩包读出来、解压、写到存放目录。现在两头都按"一小块一次往返"实现：

- 读取：`DrivePlugin::read_at(file_id, offset, length)` 是唯一的读取方式。百度插件每次调用都先请求 `filemetas` 取下载地址，再新建 HTTPS 连接发一次 `Range` 请求。解压器每次只要 8–32 KB，于是 30 GB 的包要发约 200 万次 HTTPS 请求，还会触发百度限频。
- 写入：`write_continuing` 每写一块都先 `SIZE` 查远端大小，再新开一条 FTP 数据连接 `APPE`。
- ZIP 目录：`scan_zip` 从头逐个读本地文件头，几千个文件就是上万次请求。
- 容量：ZIP64 和超过 4 GB 的单个文件直接拒绝安装，而 PS5 游戏两者都很常见。

这些问题的根源是接口形状，不是某个函数的实现，所以要先改接口。

## 决定

### 1. 读取：网盘插件提供顺序读取流

`DrivePlugin` 增加：

```cpp
class ByteStream {
 public:
  virtual ~ByteStream() = default;
  // 读到 n 字节或文件结束才返回。返回实际读到的字节数，出错时设置 error。
  virtual std::size_t read(std::uint8_t* dst, std::size_t n, std::string* error) = 0;
  virtual std::int64_t position() const = 0;
};

virtual std::unique_ptr<ByteStream> open_stream(const std::string& file_id, std::int64_t offset,
                                                const CancelToken& cancel, std::string* error) = 0;
```

`read_at` 保留，只用于读 ZIP 末尾目录、文件开头签名这类少量随机读。

百度插件的实现：

- 下载地址按 `fs_id` 缓存，记下取得时间。6 小时内复用；遇到 403、410 或百度表示地址失效的错误码时重新获取。整个安装过程里，`filemetas` 只在每个分卷第一次打开和地址过期时调用。
- 一个流对应一次 `Range: bytes=<offset>-` 请求，按需从同一个响应体里 `WinHttpReadData`，一个分卷从头读到尾只用一条连接。
- 读取出错时，从当前位置重新获取地址、重新建连，最多重试 5 次，间隔 1、2、4、8、16 秒。重试对上层透明。
- WinHTTP 会话在插件实例里长期持有，复用 TCP 和 TLS。

`http.hpp` 增加一个持有会话的 `HttpClient`，提供一次性请求和流式响应两种用法；原来的 `http_send` 改成调用它。

### 2. 预读：下载和解压、写入并行

在网盘流和解压器之间加一层 `PrefetchReader`：

- 后台线程从 `ByteStream` 读，每块 4 MB，最多攒 8 块（PC 默认 32 MB）。PS5 版可以把块数调小。
- 解压器从内存块里取数据，任意小的读取都不碰网络。
- 下载和"解压加写入"同时进行。否则总耗时是两者相加，并行后接近两者中较慢的那个。

跳转的处理：

- 向前跳不到 1 MB 时，读出来丢掉。
- 其余情况关闭当前流，在新位置重新打开。用于 RAR 跳过已完成的文件、ZIP 定位到某个条目。

### 3. ZIP：读中央目录

- 用 `read_at` 读最后一个分卷末尾最多 64 KB，找到目录结束记录；有 ZIP64 定位记录时，再读 ZIP64 目录结束记录。
- 一次读出整个中央目录，拿到每个条目的大小、CRC、所在分卷号和本地文件头偏移。大小和 CRC 以中央目录为准，因此"文件头里没写大小"（标志位 8）的条目也能处理。
- 解压时按（分卷号，偏移）排序，顺序流过压缩包；每个条目的本地文件头在流里顺手读掉，用来算数据起点。
- 分卷 ZIP 的偏移按分卷号分别计算，不再把所有分卷当成一段连续数据。
- 所有大小和偏移改成 64 位，去掉 4 GB 限制。RAR 一侧同样去掉"单个文件超过 4 GB 不能安装"的判断。

### 4. 写入：一个文件一个写入流

`InstallSink` 增加：

```cpp
class FileWriter {
 public:
  virtual ~FileWriter() = default;
  virtual std::string write(const std::uint8_t* data, std::size_t size) = 0;
  // 正常结束时调用。FTP 在这里关闭数据连接并确认 226。
  virtual std::string finish() = 0;
};

virtual std::unique_ptr<FileWriter> open_writer(const std::string& path, std::string* error) = 0;
```

- 本机目录：打开一次文件，连续写，`finish` 时关闭。
- FTP：`open_writer` 时发一次 `STOR` 并打开数据连接，之后的 `write` 只往数据连接里发数据，`finish` 时关闭并读 226。每个文件固定 3 次命令往返，和文件大小无关。
- 删除 `write_continuing` 和每块一次的 `SIZE` 检查。

续传仍按文件为单位：中断时没写完的文件从头再写，已经校验通过的文件跳过。这和现在实际的行为一致，只是不再假装能从文件中间接着写。

### 5. 进度日志：只追加

- 日志改为 `.panplay-journal.jsonl`，每完成一个文件记一行。~~每个文件追加一次~~ → 攒够 100 行或隔 1 秒追加一次（FTP 用 `APPE`），安装结束、中断、出错时写掉剩下的。中断时最多丢最近一批，那几个文件续装时重新解压。
- 读取时忽略无法解析的最后一行，这是中断造成的半行。其余行损坏时把整份日志当作空的，已完成的文件会重新解压校验，结果仍然正确。
- 去掉 1 MB 的读取上限。

### 6. 取消

`CancelToken` 从安装任务一路传到网盘流、预读线程和写入流。取消时关闭网络句柄，让阻塞中的读写立刻返回。暂停就是"取消 + 保留暂存区"，界面和队列放在下一步，但 P0 先把取消路径打通。

### 7. 百度会话

预读线程会在长时间安装中刷新令牌，所以百度插件改为进程内单例：刷新令牌时加锁，刷新前先重读会话文件；会话文件先写临时文件再改名。

## 测试

假网盘改造：

- 内容由生成函数按偏移现算，不放进内存，因此可以模拟超过 4 GB 的文件和 ZIP64 包。
- 可以配置每次请求的延迟，并统计 `filemetas` 次数、流的打开次数和 `read_at` 次数。
- 可以在指定位置注入断线和地址失效。

自测里加以下断言：

- 读 1 GB 时，流的打开次数不超过分卷数加重试次数，`read_at` 次数是个位数。
- 有几千个小文件的 ZIP，扫描目录只需要个位数的读取。
- 用 ZIP64 包和含超过 4 GB 单个文件的 RAR 能安装成功，CRC 正确。
- 中途断线后自动重连，最终结果正确；取消后能在 1 秒内停下。
- FTP 写入：每个文件的命令往返次数是固定值，不随文件大小增长。

## 验收

- 用一款含超过 4 GB 单个文件的真实游戏，从百度装到 dummy FTP，一次成功。
- 安装期间 `filemetas` 的调用次数约等于分卷数。
- 本机测速时，下载速度接近同一网络下浏览器直接下载这个分卷的速度。

## 影响

- `zip_install.cpp`、`rar_install.cpp`、`install_sink.cpp`、`baidu_drive.cpp`、`http_winhttp.cpp` 都要改，RAR 读取回调改为经过预读层。
- 进度日志的文件名和格式变了。旧格式的日志读不出来时按空日志处理，已完成的文件会被重新解压一遍。
- 内存占用增加约 32 MB 的预读缓冲。

## 实测后补充（PPSA05106，1.5 GB RAR，解压后 3 GB）

- UnRAR 默认的“快速打开”会在读每个文件头前跳到包尾读索引，再跳回来，一个包重连 50 多次。打开压缩包时关掉（`dll.cpp` 里 `QOpenMode=QOPEN_NONE`）。
- UnRAR 读完文件头会往回退几十字节重读。预读层保留刚读完的一块，往回跳不出这块就不重连；往前跳 8 MB 以内也不重连，直接丢弃中间数据。
- dlink 每次都会重定向到下载节点。记下节点地址，后续请求直接发过去，单次小范围读从约 0.55 秒降到约 0.14 秒。
- ~~列 RAR 目录改为按需小范围读（每次 64 KB），不开长连接。~~ 已去掉单独列目录，见下一节。
- 结果：安装从 104 秒降到 35～45 秒。解压期间写出约 2 秒、解压加校验约 7 秒，其余时间都在等下载；单连接下载在 33～53 MB/s 之间波动。

打开调试日志（设置里的「详细日志」，或环境变量 `PANPLAY_LOG=debug`）后，安装会记下重连、跳转和各阶段耗时。

## 实测后补充（PPSA25381，20 GB 五卷 RAR 加一个固件补丁 ZIP，约 2.5 万个文件）

- 这套 RAR 没有快速打开记录，列目录只能逐个文件头跳着读，每个文件头一次网络请求，约 0.25 MB/s，小文件多时要几十分钟，而且读完基本等于把整包下一遍。所以 RAR 不再单独列目录：一遍解压到暂存区，同时记下条目，解压完再定游戏根目录、搬到正式目录。安装中不知道文件总数，进度按已读的压缩包字节算。
- 判断已安装不再比对整份文件清单（RAR 要读完才有）。完成标记里加 `source`：网盘上各压缩包的文件名和大小，再次安装时只比这个。旧标记没有这项，再装会重装一遍。
- 一个目录里有多个压缩包时，各自解压到暂存区的 `<序号>/` 下，各自找游戏根目录。带 `param.json`/`param.sfo` 的是游戏本体，其余（如固件补丁）覆盖上去；同一层里重名仍报错。
  - 后改为按层叠放，支持多个正式补丁：带 param 的层（本体、正式补丁）在前、不带的（固件补丁）在后，同类里游戏目录里直接放的在前、子目录按名字自然排序，后叠的覆盖先叠的。只有同一处的两个固件补丁改了同一个文件才报错。完成标记里按顺序记下每层（分卷文件名和大小、带不带 param），网盘里只是插进了新层时，保留前面没变的层，从第一个新层起重叠，不重下本体。规则和使用方法见 [网盘游戏目录整理指南](../game-folder-guide.md)。
- RAR5 跨卷文件在前面各卷文件头里记的是本卷那段数据的 CRC，不是整个文件的。跨卷文件只比大小，整个文件的 CRC 由 UnRAR 在最后一卷校验。
- FTP 每个文件一条数据连接，由本机先关，关掉的连接在 TIME_WAIT 里占本机端口约两分钟，约 7800 个文件就把 16384 个临时端口用光。数据连接打开 `SO_REUSE_UNICASTPORT` 并先绑端口 0，系统在 `connect` 时按四元组选端口，TIME_WAIT 中的端口可以连别的地址。实测 TIME_WAIT 到 1.5 万时仍正常。
- 结果：从点安装到装完约 15 分钟，解压阶段约 50 MB/s、每秒约 150 个文件；装完再点安装 4 秒内显示已安装。

## 加入 7z

- 和 ZIP 一样先读目录：7z 的目录在包尾，用 LZMA SDK 的 `SzArEx_Open` 读，底下是按 256 KB 一段随机读网盘的输入流，读过的一段缓存起来。分卷 `.7z.NNN` 只是直接切开，拼起来就是一个文件。读完目录就知道全部文件、CRC 和游戏根目录，和 ZIP 一样只解根目录里的文件。
- 不用 SDK 的 `SzArEx_Extract`：它把整个块解到内存里，固实包一个块可能有几十 GB。自己写流式解码：块的压缩数据经 `VolumeStream`（多卷顺序流，和 ZIP 共用，底下是预读层）进 `LzmaDec` / `Lzma2Dec`，再过 BCJ 类过滤器，按块里的文件顺序切开写出。块里不需要的文件（根目录外、上次已装好）解码后丢掉，块里最后一个要装的文件解完就不再往下读。
- 只支持一个主方法（存储、LZMA、LZMA2）后面最多接一个过滤器（x86 BCJ、ARM、ARM64、ARMT、PPC、SPARC、IA64、RISC-V、Delta）。块描述里编码器的先后不固定（同一个包里见过两种顺序），按"哪个编码器读压缩流、绑定把谁的输出接到谁的输入"认，不按位置认。PPMd、BCJ2、AES 在读目录时就拒绝，不开始下载。
- 字典按 `min(字典, 块解压后大小)` 分配，小块不用为大字典占内存。超过设置里的字典上限（默认 PC 4 GB、PS5 512 MB，RAR 也按它查）时读完目录就拒绝。
- 续传和 ZIP 一样按文件：进度日志里有的文件跳过；块里还有要装的文件时从块开头重新下载解码，已装好的只解码不写。固实大块中断后要重下这一块已经过去的部分，这是固实压缩本身决定的。

## RAR 续装点

- 原来续装 RAR 要从第一卷顺着压缩包走一遍：非固实的已装文件用 `RAR_SKIP` 跳过，但跳过 16 MB 以内的数据时预读层是读出来丢掉，小文件多的包基本等于把前面的卷重下一遍。界面上这段显示“正在核对”，几十 GB 的包要很久。
- 现在每写完一个 RAR 里的文件，进度日志那一行多记三项：`vol`（UnRAR 此时停在第几卷）、`next`（这一卷里下一个文件头的真实偏移）、`vsize`（这一卷的大小）。`RARProcessFileW` 返回时 UnRAR 已经读过紧跟的服务头并退回到下一个文件头的开头，所以这个位置就是下一个文件的起点。目录条目记成 `{"dir":"…"}` 一行。
- 续装时取这个压缩包最后一个带续装点的文件。那一卷的大小要和日志里的一样，并且要读得懂卷头：RAR5 是签名加主文件头，RAR4 是标记头加 `MAIN_HEAD`，读前 256 字节就能拿到卷头长度。满足这两条，就把这一卷拼成“卷头 + 续装点之后的数据”交给 UnRAR，读取、跳转、报告位置都按拼接后的偏移换算。UnRAR 读到的第一个文件就是上次没装完的那个，前面的卷一个字节都不读，进度条直接从停下的位置开始。续装点之前的文件和目录不再经过 UnRAR，按进度日志补进条目清单，之后照常定游戏根目录。
- 接不上时退回老办法，从第一卷核对。这些情况算接不上：卷打不开；压缩包是固实的；拼接后的第一个文件头读不出来，或者带着“接前一卷”“固实”标记。退回发生在写任何文件之前，所以结果和老办法完全一样。旧版本写的日志没有续装点，也走老办法。
- 7z 和 ZIP 不变：ZIP 本来就按中央目录直接跳到要装的文件；7z 固实块只能从块开头解码。

## 诊断日志

为了按实测决定连接数和请求长度，打开「详细日志」后预读层和 PS5 的 HTTP 层会记下面这些。界面上的速度是解压器读到的位置，等于"下载"和"解压加写入"里较慢的那个，单看它分不出瓶颈在哪，要看这里。

- `第 2/5 卷用预读 #7`、`RAR 分卷 xxx.part2.rar 用预读 #7`：分卷和预读编号的对应。
- `预读 #7：文件 …，4096.0 MB，8 条连接 × 8.0 MB 块，最多 16 块`：这一卷的配置。
- 每 10 秒一行 `预读 #7：近 10.0 秒 …`，结束时一行 `预读 #7 结束：…` 是整卷的总账，字段相同：
  - `下载 X MB/s`：这段时间从网络收到的字节；`平均在下 N 条，每条 Y MB/s`：同时在下载的连接数按时间平均，和每条连接的实际速度。
  - `读走`：解压器取走的速度。
  - `读取方等数据 P%`：解压器因为没数据干等的时间占比。高说明下载是瓶颈。
  - `缓冲满 Q%（平均存 K 块）`：缓冲到上限、下载线程停着等解压的时间占比。高说明解压或写入是瓶颈，多开连接没用。
  - `请求 R 次（首字节平均 / 最长）`：每次请求从发出到收到响应头的时间，包括复用或新建连接。
  - `下完 B 块（平均 / 最长 秒）`：一块从开始请求到下完的时间。`首字节平均 ÷ 块平均` 就是请求开销在每条连接上的占比。
  - `打开失败`、`中途断开`、`跳转重来`：只有发生时才出现。
- 每次从头开始下载时，前 2×连接数 个请求逐条记 `块 @… 请求 …，首字节 … ms` 和 `块 @… 下完，用 … 秒（… MB/s）`，看得出连接是不是同时建起来的、每条一开始的速度。之后只记首字节超过 1 秒、重试、断开的请求。
- 跳转重来时记 `预读 #7：跳转 A -> B，丢掉缓冲里没读的 X MB，N 块正在下的作废`。
- PS5（`http_posix.cpp`）上每条新连接本来就记 `连接 … 已建立（TLS），耗时 … ms`；现在连接没还回连接池时也记原因，带上这条连接用了几次、连了多久：服务器要求读完就关、复用失败（服务器已经关了）、被中止、读的时候出错、响应没读完、空闲超过 20 秒、空闲的已经够多、收到跳转。正常读完还回池的不记。PC 上 WinHTTP 自己管连接池，看不到这些，只能从首字节时间判断。

怎么用这些数据定方案：

- `读取方等数据` 低、`缓冲满` 高：瓶颈在解压或写入，下载方案不用动。
- `读取方等数据` 高：瓶颈在下载。再看 `每条` 速度：换不同连接数（`--connections`）时每条速度基本不变、总速度跟着涨，说明是百度按连接限速，多开有用；总速度不变、每条速度跟着降，说明带宽已经跑满，少开连接、加长每次请求更省。
- 新建连接远多于"开头那几条"时，看关闭原因：多是"服务器要求读完就关"或"复用失败"，说明服务器按次数或空闲时间关连接，请求长度要加长；多是"被中止"，说明跳转太多。

## 已定

1. 续传粒度保持按文件，不做"大文件从中间续"。
2. 单连接时预读缓冲 4 MB × 8 块（32 MB）就够了（多连接的默认值见第 3 条）。`panplay bench-prefetch` 模拟下载每 48 MB 卡 0.4 秒、写入每 32 MB 换文件卡 0.3 秒，256 MB 数据：

   | 缓冲 | 下载 40 / 写 60 MB/s | 下载 60 / 写 60 MB/s |
   |---|---|---|
   | 256 KB | 36.7 秒 | 36.5 秒 |
   | 4 MB × 1 | 15.6 秒 | 13.8 秒 |
   | 4 MB × 2 | 10.6 秒 | 9.3 秒 |
   | 4 MB × 4 | 9.1 秒 | 7.5 秒 |
   | 4 MB × 8 | 8.9 秒 | 7.0 秒 |
   | 4 MB × 16 | 8.9 秒 | 7.0 秒 |
